# C5: a rollback on one hub holds on every hub

**Date:** 2026-11-20 · **Fork commits:** `fe76618dc` … `48a00a091` (4 red → green pairs)
· **Lab image:** `argocd-multihub:48a00a091`

## Summary

E5 is re-run on the fork. hub-b rolls back while hub-a has auto-sync with
self-heal on.

| | Stock v3.6.1 (baseline E5) | Fork, C1 + C2 + C3 + C5 |
|---|---|---|
| Rollback survives | **no:** hub-a self-healed it back in **1s** | **yes:** the spoke stayed on the rolled-back generation for the whole 4-minute watch (and until it was cleared) |
| What the rolling-back hub shows | `Synced` + `Succeeded` while the spoke ran the newer version | **OutOfSync** against HEAD, which is true |
| What the other hub shows | (it reverted) | OutOfSync, auto-sync on, plus one `MultihubAutoSyncPaused` Event naming the override, who set it, and how to clear it |
| Back to normal | n/a | a user sync to HEAD on **either** hub clears the override; automated syncs resume |

## Design (as built)

A single Argo CD refuses a rollback while auto-sync is on. C5 extends that
rule across hubs: a rollback on any hub pauses automated syncs on every hub.

- **Record.**
  - A hub records an **override** on the app's Lease when it starts a new
    operation that is:
    - a user's sync (not automated),
    - of the whole app (not partial or dry-run, single-source),
    - to a revision other than the app's `targetRevision`.
  - Argo's Rollback is exactly that (the history entry's SHA).
  - The override is four annotations: `override-revision`, `-by`, `-at` and
    `-reason`, where the reason is e.g.
    `sync to 5332ef8… by lab-rollback`.
  - It's written after the operation lease is taken and **before** syncing.
    If it can't be written, the operation fails: it would otherwise be
    silently reverted.
- **Honor.** Just before taking the operation lease for an automated sync
  (self-heal included), a hub checks for an override. With one in place it
  stands down.
  - It logs `overridden` (info when it changes, like lease refusals) and
    raises one `MultihubAutoSyncPaused` Event.
  - If the override can't be read, it also stands down.
  - Comparison isn't changed, so both hubs show the truth: the live state
    differs from HEAD.
- **Clear.** A user's full sync to the `targetRevision` (or with no
  revision) on any hub clears it, with `override_cleared` and a
  `MultihubOverrideCleared` Event. Deleting the annotations by hand also
  works.
- **Telemetry:**
  - `override_set` and `override_cleared` on the new path `override`
    (info, Normal Events).
  - `overridden` on the same path.
  - All are counted in `argocd_multihub_lease_decisions_total`.

The design doc had proposed comparing every hub at the override revision.
Pausing auto-sync was chosen instead because:
- it matches single-hub Argo, which also makes the operator turn auto-sync
  off;
- it keeps the sync status honest;
- the override value is only informational, so a sync to another branch
  works the same way.

```
15:08:45 hub-b: override_set   override to 5332ef8… recorded (sync to 5332ef8… by lab-rollback); automated syncs are paused on every hub until a sync to spike/multi-hub
15:08:46 hub-b: released operation lease
15:08:46 hub-a: overridden     Skipping auto-sync: override to 5332ef8… in place (…, recorded by hub-b); sync to spike/multi-hub on any hub to resume automated syncs
```
```
--- 15:08:49
hub-a OutOfSync op=Succeeded by=true(auto) rev=f531eae…
hub-b OutOfSync op=Succeeded by=lab-rollback rev=5332ef8…
spoke generation=17
spoke image=registry.k8s.io/pause:3.10
override=5332ef8… by=hub-b
```

- **Nothing changed for the rest of the 4-minute watch.** hub-a, with
  self-heal on and the app OutOfSync, started no operation. In stock E5, it
  reverted the rollback in 1s.
- **hub-a raised one Event** (`MultihubAutoSyncPaused`, count 1) and logged
  one info line. Later refreshes were collapsed to debug.
- **hub-b shows OutOfSync.** In stock E5 it showed `Synced` + `Succeeded`
  while the spoke ran the version being rolled back *from*.

```
15:13:05 hub-a: operation lease acquired (generation 38)
15:13:05 hub-a: override_cleared override to 5332ef8… (…, set by hub-b) cleared by a sync to spike/multi-hub by lab-manual-sync; automated syncs resume on every hub
15:13:26 hub-a: released operation lease
--- 15:13:29
hub-a Synced, hub-b Synced; spoke generation=19, image busybox:1.36; override=(none)
```

Then hub-b's auto-sync was turned back on and one commit was pushed. hub-a
auto-synced it (`092bb70`, one hook Job), and both hubs ended Synced at
generation 20.

**Side observation, not caused by C5:**
- 16s after that auto-sync, hub-a started a second, partial **self-heal of
  the ConfigMap**, which reported `configmap/lab-config unchanged`
  (`hub-a-resume-controller.jsonl`).
- The comparison that triggered it was taken while hub-a's own sync was
  still before wave 1 (the ConfigMap is wave 1 since the E10 lab change),
  and auto-sync acted on it as the sync completed.
- It's a write-free extra operation. It looks like single-hub
  stale-comparison behavior made visible by the new sync wave. It is not a
  second hub acting. Not investigated further here.

## Known gaps

1. **Multi-source apps** never record an override. Their rollback is still
   reverted by other hubs.
2. **What counts as a rollback:** it's classified from the operation
   (user-initiated + specific revision ≠ `targetRevision`). A user sync to a
   *different branch* also pauses everyone, which is arguably right. A user
   sync that names the targetRevision's current SHA explicitly also pauses,
   because it doesn't equal the branch name. The second case is probably
   wrong.
3. **Re-enabling auto-sync on the rolled-back hub doesn't clear the
   override.** Only a user sync to HEAD does. An operator who just flips
   auto-sync back on sees `MultihubAutoSyncPaused` until they sync.
4. **Override changes aren't fenced against an in-flight operation.** A user
   sync to HEAD started while another hub's rollback is still running waits
   for the lease (C2), then clears the override. That's the last action
   winning, which seems right, but it wasn't tested.
5. **Parameter overrides** (the other half of F6) aren't handled.
