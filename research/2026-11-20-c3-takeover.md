# C3: taking over an operation when its hub dies

**Date:** 2026-11-20 · **Fork commits:** `954fefa93` … `b305e8cc3` (5 red → green pairs)
· **Lab images:** `argocd-multihub:b305e8cc3` (C3), `fcc7bafb4` (C3 before the
fix below), `c67b396e7` (control: C1 + C2, no C3)

## Summary

If the hub running a sync dies partway through, the other hub now finishes
**that same operation**. It doesn't start a new one, so a hook that was
already running is adopted and runs once.

|  | Control (C1 + C2) | C3 |
|---|---|---|
| PreSync hook runs when hub-a dies mid-hook (E8) | **2**, overlapping for ~60s | **1** (hub-a's Job, adopted) |
| Operation hub-b runs | a new auto-sync (new `startedAt`) | hub-a's operation (same `startedAt`, initiator, progress) |
| hub-a, coming back after hub-b finished | **resumes its stale operation** and runs the sync phase again | takes hub-b's result; runs nothing |
| Time from hub-a's last lease renewal to hub-b running | 60s lease + ~3s | 60s lease + ~3s |

The first live run found a bug the unit tests had missed: the takeover kept
fields from hub-b's previous operation, and hub-b ran the hook twice anyway.
It was fixed test-first and re-run (R2).

## Design (as built)

Everything lives on the Application's existing Lease on the spoke, next to
the C2 holder and the C1 pin.

1. **Mirror.**
   - After every operation pass, the lease holder writes its full
     `OperationState` to the annotation `multihub.argoproj.io/operation`.
     That includes `startedAt`, which names generated hooks, and the
     per-resource results, which say which hooks already ran.
   - The value is `base64(gzip(header JSON + "\n" + state))`, capped at
     200KiB. It's **fenced**: written only by the holder at the generation
     its pass ran under, so a hub whose lease was taken can't overwrite the
     new holder's mirror.
   - The final state is mirrored *before* the lease is released.
2. **Claim.** In the refresh loop, just before auto-sync, a hub with no
   operation of its own checks the mirror.
   - If the mirror shows another hub's operation still **running**, and that
     hub's lease has **expired** (or was released without finishing), the
     hub takes the lease in one compare-and-swap. That gives a new
     generation, and the operation is re-mirrored under the claiming hub, so
     a third hub sees a live holder and waits.
   - The claiming hub then writes the operation and its state onto its own
     Application, replacing both whole. The operation queue resumes it.
   - Because the claimed operation sets `app.Operation`, auto-sync skips
     that refresh.
   - The operation keeps its initiator and gets
     `info: multihub=taken over from <hub>`.
3. **Follow.** At the top of each operation pass, a hub with an in-progress
   operation first checks the mirror.
   - If another hub has recorded the **same** operation (same `startedAt`),
     this hub copies that hub's state and doesn't sync.
   - While the operation runs elsewhere, the hub re-checks every
     `multihubOperationWait`. Once it's finished, the hub keeps the result
     and requests a refresh.
   - A *different* operation on the mirror keeps the C2 behavior: the hub
     stops with an error while another hub holds the lease.

**Telemetry:**
- `takeover` on the new path `takeover`: warn, plus a `MultihubLeaseTakeover`
  Warning Event.
- `following`: info on change, plus a `MultihubOperationTakenOver` Event.
- `mirror_error`: warn on change.

All three are counted in `argocd_multihub_lease_decisions_total`.

## R2. The first run: a bug that ran the hook twice (`e8-first/`)

The same experiment on `fcc7bafb4` had a working claim: the lease expired at
12:53:56 and was claimed the same second. But the Job's creation time moved
from 12:52:54 to **12:54:31**, and hub-b's message went through `waiting for
deletion of hook`. hub-b had deleted hub-a's running hook and created it
again under the same name.

hub-b's log shows why:
```
12:53:56 multihub: took over the running operation from hub-a ...
12:53:56 Retrying operation. Attempt #0
```

- The takeover wrote the mirrored state with a JSON **merge** patch. hub-b's
  Application still held its own previous, finished operation. Merging kept
  every field the mirror leaves out, including that operation's
  `finishedAt`.
- A Running operation with `finishedAt` set is how Argo CD marks a pending
  **retry**. So hub-b dropped the mirrored results and started from scratch.
  The hook then had no result, and with
  `hook-delete-policy: BeforeHookCreation`, gitops-engine deletes a live hook
  that has no result before creating it.
- The unit fixture had no previous operation on hub-b, so the tests missed
  this.

**Fix (pair 5):**
- A red test with a previous finished operation on hub-b reproduced it.
  `finishedAt`, `retryCount`, the retry strategy and `revisions` all leaked.
- The green commit replaces `/operation` and `/status/operationState` whole,
  with a JSON patch.
- R1 is the re-run.

**Correction to the design doc (F5):**
- Same `startedAt` + revision gives the same hook *names*, but that alone
  doesn't adopt a running hook.
- The hook's entry in the operation's per-resource results is what marks it
  as started. Without it, `BeforeHookCreation` deletes and re-creates the
  hook.
- C3 works because the mirror carries those results. Both the results and
  the timestamp have to transfer exactly.

```
--- 13:15:58
hub-b Running startedAt=2026-11-20T13:15:53Z by=auto rev=5332ef8 | waiting for completion of hook batch/Job/lab-presync-5332ef8-presync-1795180553
lab-presync-5332ef8-presync-1795180490   2026-11-20T13:14:51Z   <none>
lab-presync-5332ef8-presync-1795180553   2026-11-20T13:15:53Z   <none>

lab-presync-5332ef8-presync-1795180490   2026-11-20T13:14:51Z   1
lab-presync-5332ef8-presync-1795180553   2026-11-20T13:15:53Z   <none>
```

- When the lease expired, hub-b's auto-sync took it over
  (`takeover auto-sync … generation 27`) and started a **new** operation
  (new `startedAt`). So it ran a **second** hook Job, which ran alongside
  hub-a's orphaned one for about 60s: from 13:15:53 until hub-a's 120s hook
  ended at about 13:16:55. It showed as done at the 13:17:14 check.
- **hub-a returns** (13:18:27, 12s after hub-b released):
  ```
  13:18:27 multihub: operation lease acquired (generation 28)
  13:18:27 Resuming in-progress operation. phase: Running, message: waiting for completion of hook batch/Job/lab-presync-5332ef8-presync-1795180490
  13:18:27 multihub: released operation lease
  ```
  - The lease was free, so C2 let hub-a resume its stale operation. Its
    hook had finished, so no third Job ran, but it **ran the sync phase
    again** after hub-b's sync was done.
  - With a longer gap, or a hook that hadn't finished, that would be a
    second full run.
  - `syncs.sh` doesn't show it, because it counts *new* operations only.

## Known gaps

1. **How fast a takeover happens depends on the next refresh.**
   - Here hub-b refreshed every ≤15s because its auto-sync was waiting on
     the lease. If hub-b had no reason to refresh, for example a manual sync
     on hub-a of an app that hub-b sees as Synced, the claim waits for hub-b's
     next periodic refresh (minutes).
   - Fix: when a refresh sees a running mirror held by another hub, requeue
     a refresh for when that lease expires. Not live-tested; next red test.
2. **Manual operations and an app that's Synced on hub-b** were not run
   live. Only an auto-sync operation was taken over.
3. **A failed claim strands the operation for this hub.**
   - If the claim's lease write succeeds but writing the Application fails,
     the mirror says the operation belongs to this hub, so this hub won't
     claim it again. Another hub can, once the lease expires.
   - With two hubs and the other one down, that operation is stuck.
4. **`finishedAt` on the returning hub** is when it found out about the
   result (13:09:00), not when hub-b finished (13:08:50).
   `setOperationState` stamps it.
5. **One extra Lease write per operation pass** (the mirror) and one extra
   read per pass for in-progress operations (the follow check). Mirrors
   aren't compressed against the previous one. A large app's results could
   hit the 200KiB cap (`mirror_error`), and its takeover would then restart
   the operation.
6. **Mid-sync-phase death** was not tested: hub-a dying while applying
   resources rather than during a hook. The design resumes from the
   per-resource results the same way, so it should behave the same.
